Waypoint: self-hosted issue tracker. Go backend (internal/), React app in web/ embedded via web/embed.go.
- All reads/writes go through internal/core.Service with an *Actor; it does access checks. Never query the DB from internal/api.
- internal/core is being split into layers (WP-ADR151): internal/core/kernel holds what every domain needs and imports no domain; a domain is internal/core/<domain>, importing only kernel and domains below it; core.Service stays the facade. Code that needs nothing from package core goes in such a package, not in core; in core, use kernel's names for new code (kernel_shims.go keeps the old ones for existing code).
- Mutations: Service.write + t.emit(Event); side effects happen in dispatch (events.go), not inline.
- Schema changes: add internal/db/migrations/000N_*.sql (forward-only).
- Frontend data: add a factory to web/src/lib/queries.ts; reuse components/ui primitives; Tailwind tokens from index.css.
- Verify: `make check` runs scoped checks for what changed (`make check-all` is the full tree); web changes also need `cd web && npm run typecheck && npm run format:check` (`npm run lint` is dormant until typescript-eslint supports TypeScript 7; see web/eslint.config.mjs); UI changes also need a real browser check (Playwright) at desktop and 390px widths.
- Prove bug fixes with a behavioral test against the existing package/public surface (not a newly invented private helper) that fails before the fix and passes after.
- Ship a PR via `wp ship`
- Use `wp code find` and `wp code show FILE:SYMBOL` instead of long grep/sed chains. Use `probe` or `fanout-coordinator` to investigate and verify claims with evidence; plans, decisions, and architecture should come from the main thread.
- Solve user intent directly rather than codifying positional/threshold proxies; treat prior agent-filed tasks, ADRs, and comments as hypotheses to verify against current code (`origin/main`), not immutable requirements.
- Diagnose production with `wp server status|log|metrics` and `wp ai usage` (admin token; docs/DEPLOY.md "Diagnosing production"), not ssh; ssh is for incidents a person runs.
- Prefer a request (`wp request ask|change|run|todo`) to stopping when a hook or the permission classifier blocks you or a person must decide; add `--followup never` when you won't act on the answer.
- Docs: how each feature works is in WP feature notes (`wp design ls --kind feature`, `wp design show N`); a change that alters what a note says edits it in the same task (`wp design edit N -f FILE`). Running Waypoint: docs/DEPLOY.md. CLI: `wp help --all`.
- Waypoint tracks itself in project WP; `wp` (run in this repo) reads and records there. Where a skill names CONTEXT.md or docs/adr, use these instead:
  - Domain language: the WP glossary (`wp define TERM`, `wp glossary add|edit`; first line a one-sentence definition, `--avoid` for rejected synonyms).
  - Decisions (ADRs): WP design notes of kind decision (`wp design ls --kind decision`, `wp spec ADR7`, `wp design new decision "…"`), linked as `ADR7` / `WP-ADR7` / `[[ADR7]]`. A decision written for a person-filed task (`--for WP-177`) applies immediately—don't call it approved or accepted, since the task link explains why it counts. A decision on your own initiative or an agent-filed task is a proposal until approved, and later agent edits to an approved decision stay pending. Legacy decision pages (`WP-D1…`) remain readable via `wp page show`.
  - Plans, experiments, measurements, review notes: WP pages (`wp page ls --category plan`, `wp page show WP-PL3`, `wp page new plan "…"`). Code comments cite decisions by code (WP-D11, WP-ADR7).
  - Work items: WP issues (`wp ls`, `wp new`, `wp next`).
