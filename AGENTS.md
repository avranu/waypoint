Waypoint: self-hosted issue tracker. Go backend (internal/), React app in web/ embedded via web/embed.go.
- All reads/writes go through internal/core.Service with an *Actor; it does access checks. Never query the DB from internal/api.
- Mutations: Service.write + t.emit(Event); side effects happen in dispatch (events.go), not inline.
- Schema changes: add internal/db/migrations/000N_*.sql (forward-only).
- Frontend data: add a factory to web/src/lib/queries.ts; reuse components/ui primitives; Tailwind tokens from index.css.
- Verify: `make check` (vet + tests + golangci-lint + gosec + govulncheck); web changes also need `cd web && npm run typecheck && npm run format:check` (`npm run lint` is dormant until typescript-eslint supports TypeScript 7; see web/eslint.config.mjs); UI changes also need a real browser check (Playwright) at desktop and 390px widths.
- Ship a PR via `wp ship`
- Most claude code spend is Fable and opus main threads reading code and writing the implementation themselves, while `wp code show FILE:SYMBOL` and `wp code find` went unused. Consider using a `probe` or `fanout-coordinator` to gather data, and sonnet agents for well defined work. Plans, decisions, and architecture should come from the main thread.
- Diagnose production with `wp server status|log|metrics` and `wp ai usage` (admin token; docs/DEPLOY.md "Diagnosing production"), not ssh; ssh is for incidents a person runs.
- Prefer a request (`wp request ask|change|run|todo`) to stopping when a hook or the permission classifier blocks you or a person must decide; add `--followup never` when you won't act on the answer.
- Docs: how each feature works is in WP feature notes (`wp design ls --kind feature`, `wp design show N`); a change that alters what a note says edits it in the same task (`wp design edit N -f FILE`). Running Waypoint: docs/DEPLOY.md. CLI: `wp help --all`.
- Waypoint tracks itself in project WP; `wp` (run in this repo) reads and records there. Where a skill names CONTEXT.md or docs/adr, use these instead:
  - Domain language: the WP glossary. `wp define TERM` (a word to avoid answers with the one to use); record new or sharpened terms with `wp glossary add|edit` (first line a one-sentence definition, `--avoid` for rejected synonyms).
  - Decisions (ADRs): WP design notes of kind decision, not pages and not markdown in the repo (`wp design ls --kind decision`, `wp spec ADR7` or `wp design show ADR7` for the text and who wrote and approved it, `wp design new decision "…"`). Codes are `ADR7` per project, `WP-ADR7` from elsewhere (`ADR-0007` works too), and `[[ADR7]]` links them. A decision you write to carry out a task a person filed counts on that person's request, not left for approval: name the task, `wp design new decision "…" --for WP-177`, and it shows "written for WP-177, which Jess filed" (your later edits to it apply directly). Nobody approved it, so don't call it approved or accepted: the link to the task says why it counts. A decision you make on your own initiative, or for a task an agent filed, is a proposal until a person approves it, and an agent's later edit to an approved one stays pending (`wp design edit`, `wp design add`), so the approved text is what counts. The decisions already recorded as pages (WP-D1…) stay readable (`wp page show WP-D7`) until they are converted.
  - Plans, experiments, measurements, review notes: WP pages (`wp page ls --category plan`, `wp page show WP-PL3`, `wp page new plan "…"`). Code comments cite decisions by code (WP-D11, WP-ADR7).
  - Work items: WP issues (`wp ls`, `wp new`, `wp next`).
